# 共享预算与恢复规划验收场景

依据及测试记号见 [验收入口](README.md)。本文件所有场景均为 **NOT_RUN**，尚无协调器或 APK 可供执行。`B` 为 GUI 总额度，`G` 为已发起 GUI 尝试数，`P` 为已发起 Planner 尝试数，`V` 为本轮已进入的只读阶段数。次数均按实际尝试记账，不按成功响应数。

## BP-01｜跨原任务、人工、查证及恢复共用额度

**P0 · C＋A；D 复核显示与真实尝试数。**

- **前置**：设置 `B=6`；原任务已执行两次 GUI 请求，`G=2,P=0,V=0`；当前无在途输入。
- **事件**：接管 → 人工自由操作 → 归还 → P1=INCOMPLETE＋VERIFY → GUI wait → GUI finish(completed，表示取得查证证据) → P2=INCOMPLETE＋EXECUTE → RECOVERY tap → RECOVERY finish(completed)。
- **通过**：人工前后 `G=2`；P1 后 `P=1`；wait 后 `G=3`；查证 finish 后 `G=4,V=1`；P2 后 `P=2`；恢复 tap 后 `G=5`；恢复 finish 后 `G=6`。原任务、查证和恢复的 GUI 请求共六次，没有阶段预算。最终仅记录模型声明完成，用户评价仍为 unknown。
- **失败判据**：归还／新阶段／回退清零计数，人工操作扣步，Planner 占 GUI 步，或结束声明免费。

## BP-02｜已发失败、无效输出、取消与迟到均占一步

**P0 · C＋A；网络和设备回调变体需 D。**

- **前置**：`B=30,G=7`，准备发出一次 GUI 请求。
- **事件变体**：请求进入传输后超时／API 错误；响应 JSON 或工具参数无效；多工具／未知工具／截断；发出后被接管取消；接管后迟到；有效请求返回后执行器因画面失效或设备问题拒绝动作。
- **通过**：每个独立变体均 `G:7→8`，不退款、不双扣；非法或过期动作不执行。设备动作失败不凭空产生第二次模型尝试。无隐藏格式修复或自动重试；只有流程仍允许且用户显式重试，下一实际 GUI 尝试才为 `G=9`。
- **日志断言**：同一角色＋调用序号的 started 与终态只是一笔尝试；取消后再来回调不能再次扣步或改写为成功。

## BP-03｜发送前预检失败不伪造模型调用

**P0 · C＋A；授权／取图失败需 D。**

- **前置**：`G=7,P=0`。
- **事件**：分别注入无控制权、缺少有效画面、请求体超限，在进入网络尝试之前拒绝 GUI 或 Planner 请求。
- **通过**：请求发送次数为零，`G=7,P=0`；无 model_call.started，只记录实际本地错误。进入真实网络尝试后才发生的连接失败属于 BP-02／BP-10，不能伪装成预检失败退款。
- **反例**：取图失败也扣一个 GUI 步，或记录 Planner 失败却实际偷偷补发。

## BP-04｜第 30 步不是额外结束额度

**P0 · C＋A；D 复核最终状态。**

- **前置**：默认配置显示 `B=30`，`G=29`，原任务或恢复阶段。
- **事件 A**：第 30 次 GUI 请求返回合法 finish(completed／unable)。
- **通过 A**：`G=30`；按对应阶段声明结束，不能因“结束声明也占一步”反而拒绝已经合法取得的最后一步声明。
- **事件 B**：独立重置前置条件，第 30 次只返回普通动作，动作安全执行后尚无结束声明。
- **通过 B**：不能发第 31 次请求、不能补一条免费 finish、不能把动作执行成功推断为任务完成。关闭后续自动派发，按 `budget_exhausted` 结束；保留已有动作结果。
- **设置变体**：更改为 `B=6` 时相同规则作用于第六步；新建任务才建立新的额度，旧任务不借切换页面重置。

## BP-05｜第一次 Planner 的分支与完成确认

**P0 · C＋A；D 复核只读权限。**

- **前置**：已合法归还，`P=0,V=0`，当前画面有效且有 GUI 余额。
- **事件／通过**：分别让 P1 返回下表合法输出；每种仅有一次 Planner 尝试，`P=1`。非空目标及条件按相应 Schema 验证。

| P1 输出 | 下一阶段 | V | 不允许发生 |
| --- | --- | --- | --- |
| COMPLETE＋VERIFY | 新 CONFIRM | 1 | 直接结束，或伪装为 RECOVERY 去确认 |
| INCOMPLETE＋VERIFY | 新 VERIFY | 1 | 把检查目标当成剩余执行目标 |
| UNVERIFIABLE＋VERIFY | 新 VERIFY | 1 | 擅自导航取得缺失证据 |
| INCOMPLETE＋EXECUTE | 新 RECOVERY | 0 | 自动先插入查证或继续调用 Planner |
| INCOMPLETE／UNVERIFIABLE＋FALLBACK | 原任务文本历史继续 | 0 | 撤销用户操作，或重建恢复目标 |

- **零余额变体**：已发 P1 返回 COMPLETE＋VERIFY 时若 `G=B`，不能跳过确认按完成结束，也不能伪造一次确认；按额度结束。此变体不要求预算耗尽后主动新发 P1。
- **非法输出变体**：P1 COMPLETE＋EXECUTE／FINISH 等走 BP-10 的格式错误回退，不能偷偷把模型输出修成 VERIFY 后宣称原响应合法。

## BP-06｜一轮只读阶段可以包含多步，但不能变成多轮

**P0 · C＋A＋D。**

- **前置**：P1 已选择 VERIFY 或 CONFIRM；`B=10,G=4,P=1,V=1`。
- **事件**：在同一阶段 wait → wait → finish；每次只观察当前页刷新。另以非法工具变体注入 tap、swipe、input_text、press_key、launch_app。
- **通过**：合法路径 `G:4→5→6→7`，`V` 始终为 1；不是“一轮只许一个 GUI 请求”。阶段请求只提供 wait／finish；非法工具不派发，不能借“只读导航”解释执行。已发非法决策仍占其 GUI 步，按模型／协议错误处理，不伪造成合法 unable。
- **轮次断言**：阶段结束后不得再进入 VERIFY／CONFIRM；不能通过改阶段 ID、再建一个空对话、修改检查目标或将新检查命名为 EXECUTE 规避。

## BP-07｜普通查证与最终确认的四种结束含义

**P0 · C＋A。**

- **前置**：`P=1,V=1`；尚有足够 GUI 额度发出本阶段的结束决策；返回图像有效。
- **事件／通过**：分别注入下表合法 finish，并核对下一条实际请求。

| 结束声明 | 下一步 | P | 结果含义 |
| --- | --- | --- | --- |
| VERIFY completed | P2，附最新画面及未核验报告 | 2 | 仅取得查证证据，不代表原任务完成 |
| VERIFY unable | P2，说明证据未取得 | 2 | 不能自建另一轮查证 |
| CONFIRM completed | 直接结束 | 1 | 记录确认声明来源；不自动成为研究成功标签 |
| CONFIRM unable | P2，verification_failed=true | 2 | 允许根据新的当前证据重新判断 |

- **错误区分**：设备取图失败或模型输出错误不等于合法 finish(unable)。在途输入不明时仍服从暂停屏障，不能借本场景绕过设备／协议错误处理。

## BP-08｜第二次 Planner 分支和“无第三次”的硬边界

**P0 · C＋A。**

- **前置**：普通 VERIFY 已合法结束，或 CONFIRM 合法返回 unable；`P=1,V=1`。分别从两种入口执行以下变体。
- **事件／通过**：发出 P2 前 `P:1→2`；合法输出遵守下表；P2 自身不消耗 GUI 步。

| P2 输出 | 后续 |
| --- | --- |
| COMPLETE＋FINISH，objective=""，completion_conditions=[] | 协调器直接结束，见 BP-09 |
| INCOMPLETE＋EXECUTE | 有 GUI 余额时新 RECOVERY；交付后不再规划 |
| INCOMPLETE＋FALLBACK | 有 GUI 余额时原任务文本历史继续 |
| UNVERIFIABLE＋FALLBACK | 同上，不擅自生成剩余执行目标 |

- **非法变体**：P2 VERIFY；UNVERIFIABLE＋EXECUTE；COMPLETE＋EXECUTE；FINISH 带非空目标／条件；多余字段；截断 JSON。
- **通过**：非法变体记录 MODEL／INVALID_OUTPUT，按既定原任务回退条件处理；`P=2,V=1` 不变，不发 P3、不建立第二轮只读阶段。不能把非法 FINISH 修好后冒充有效完成声明。

## BP-09｜第二次 Planner 直接结束，GUI 余额为零也无需 done

**P0 · C＋A；D 复核界面与日志。**

- **前置**：最后一个合法 GUI 步已返回 VERIFY finish(completed／unable)，或 CONFIRM finish(unable)；`B=30,G=30,P=1,V=1`，已具备 P2 入口。
- **事件**：发出 P2，返回 COMPLETE＋FINISH，空 objective 和空条件列表；包括 `verification_failed=true` 但最新证据足以支持完成的变体。
- **通过**：`P=2,G=30,V=1`；直接 ENDED。此响应之后新增 GUI 请求数、GUI finish 事件数、手机动作数和只读阶段数均为零。没有 GUI done、免费结束步、第三次 Planner 或第 31 步。
- **结果断言**：session_ended.reason=model_declared_complete，completion_source=planner；未收到独立用户评价时仍 unknown。测试中的完成证据只用于判断模型应答／流程，不成为传给模型的隐藏评分。
- **对照变体**：相同零余额前置，P2 返回 EXECUTE／FALLBACK，不能交付任何新 GUI 请求，按额度结束。另以 `G<30` 重跑 COMPLETE＋FINISH，仍直接结束而不是用剩余额度补 done。

## BP-10｜Planner 错误直接按既定路径回退，不修复重试

**P0 · C＋A；传输变体需 D。**

- **前置 A**：P1 实际尝试后出现超时／API 错误／JSON 错误／Schema 错误；当前画面与控制权仍有效，有 GUI 余额。
- **通过 A**：`P=1`；按原任务回退，恢复原任务文本历史及当前图。不能调用 P2 来修复 P1，也不能隐藏再试 P1；下一次实际 GUI 请求正常 `G+1`。
- **前置 B**：P2 实际尝试后同类错误。
- **通过 B**：`P=2`；相同回退条件成立才继续，无 P3／无第二轮只读阶段。
- **阻断变体**：当前画面或权限失效时不派发，按原阶段暂停处理；已经请求停止时保持停止意图，按屏障进入已停止，不能退回 BLOCKED 或自动回退执行。若 GUI 已无额度则按额度结束，不能靠错误回退取得新额度。错误响应原文及模型输出不持久化。

## BP-11｜执行交付后不持续重规划

**P0 · C＋A；D 复核真实错误恢复。**

- **前置**：分别从 P1 或 P2 交付 EXECUTE／FALLBACK；记住交付时 `P`。
- **事件**：GUI 连续执行若干步；分别在正常动作、finish(completed)、finish(unable)、模型错误暂停、设备错误暂停处观察后续；仅对仍允许恢复的同进程模型／设备错误，按原阶段显式重试。合法 finish 已结束任务时不能以重试重开。
- **通过**：不会因动作结束、任务未完成或普通错误再启动 Planner；`P` 始终等于交付时值。GUI 重试仍扣共享 `G`，不换任务、不新建预算。恢复执行保持其新阶段历史；回退保持原任务文本历史。
- **反例**：GUI unable 后自动请 Planner 再拆一次目标，或失败后偷偷新建另一轮接管归还。

## BP-12｜重复提交、回调和重新进入准备不重置规划额度

**P0 · C＋A；通知／悬浮入口需 D。**

- **前置**：有效归还已进入 P1；分别停在 P1 在途、只读阶段、P2 在途、已交付后。
- **事件**：重复归还、重入恢复准备、重复送达相同 Planner 响应或网络终态；在仍允许恢复的 GUI／设备错误暂停后重新进入同一阶段。Planner 错误按 BP-10 回退，不把重新进入准备当成重试 Planner 的入口。
- **通过**：相同逻辑调用不被消费两次；实际 Planner 尝试数始终 ≤2，只读阶段数 ≤1；`G/P/V` 均不清零。不能用新请求 ID、切换通知入口或新建对话绕过额度；已交付后重复回调不再交付一次。
- **已有计账**：已经发出的请求取消或失效也不退款；没有发出的重复控制事件不新增模型尝试。

## BP-13｜Planner 的迟到完成也不能覆盖停止意图

**P0 · C＋A；D 复核屏障。**

- **前置**：P1 或 P2 已发出；本地仍未将该回复提交为有效决策。
- **事件**：用户请求停止，使原请求归属失效；随后 P1 返回 EXECUTE／VERIFY，或 P2 返回 COMPLETE＋FINISH；并重放一次相同回调。
- **通过**：旧决策不交付目标、不建立阶段、不派发 GUI，也不把用户停止改成模型完成。已有 Planner 尝试照计、不退款。状态按当前停止意图及输入终态进入已停止；重复回复无作用。

## BP-14｜只读最后一步为 wait、尚未 finish 就耗尽额度

**P0 · C＋A；D 复核结束和最新帧释放。用户于本次验收讨论明确选择。**

- **前置**：VERIFY 或 CONFIRM，`B=30,G=29,P=1,V=1`，尚未收到本阶段合法 finish。
- **事件**：最后一个 GUI 请求返回 wait，计为 `G=30`；等待安全结束并取得新画面。画面可以看起来已完成，也可以仍不可确认。
- **通过**：关闭后续自动输入，按 budget_exhausted 结束；`G=30,P=1,V=1`。不请求 GUI finish、不把 wait 当成 completed、不调用 P2、不另开查证，也不由协调器生成一份“查证成功”报告替代 finish。清理帧及请求引用。
- **同类边界**：最后一次 GUI 尝试失败或输出无效、同样没有合法阶段结束声明时，不伪造 unable 来取得 P2 入口；按额度结束并保留实际错误分类。若仍有未确认输入，先关闭派发并等待／显示未确认状态，不能为结束额度绕过屏障。
- **与 BP-09 的区别**：BP-09 的最后一步已经是有效阶段结束声明；本场景没有。确认成功的最后一步则按 BP-07 直接结束。不能仅测试 `G==B` 就把这三种入口合并。

## BP-15｜错误分类与任务结果相互独立

**P0 · C＋A；D 复核最小日志导出。**

- **事件变体**：有效 GUI finish(unable)；API 错误；截图／输入设备错误；有效 P2 FINISH；CONFIRM completed；用户主观认为任务仍未完成。
- **通过**：阶段 unable 不自动归为 MODEL 错误；API／格式归 MODEL，截图／执行归 DEVICE。有效完成声明只记录来源及流程结束原因；用户评价可独立为 user_reported_incomplete。没有程序逐条件状态、额外完成门槛或自动成功布尔值。
- **数据断言**：持久化记录只满足最小事件 Schema；不包含 finish.message、Planner 目标／条件、任务、请求／响应、坐标或图像。断言和合成哨兵只在测试内存中使用。
