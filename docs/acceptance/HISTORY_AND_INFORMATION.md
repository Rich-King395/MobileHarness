# 历史隔离与信息边界验收场景

版本：验收契约 1.0.0。日期：2026-10-30。共同记号及通过条件见 [验收入口](README.md)。

**执行状态：以下 12 个场景均未执行，等待请求组装器、协调器或最小 APK 实现。** 本文是可判定的验收合同，不是运行时实现、测试通过报告或新的采集授权。

## 依据与观测方式

当前规则以 [模型适配补充 1.1.0](../MODEL_ADAPTER_AND_PROMPT_VERSIONS_v1.1.0.md)、[最小日志和数据边界](../DATA_AND_LOGGING_BOUNDARIES.md)、[请求配置 1.1.0](../../prompts/v1.1.0/request-profiles.json) 和对应提示词包为准。[1.0.0 基线](../MODEL_ADAPTER_AND_PROMPT_VERSIONS.md) 的动作、Planner 分支、预算与阶段语义继续适用；其中图片历史及持久化规则已被 1.1.0 明确覆盖。原始 [交接设计](../../HandoffHarness_APK_Handoff/HANDOFF_ANDROID_APK.md) 和 [英文提示快照](../../HandoffHarness_APK_Handoff/HANDOFF_ANDROID_APK_PROMPTS.md) 仅供追溯，不能重新引入已经修订的旧冲突措辞。

- **P0**：方法或信息边界的必要条件，相关路径交付前必须满足。**P1**：补充覆盖。
- **C**：协调器配合可控网络、采集器、执行器替身，可控制异步返回顺序。
- **A**：仅检查请求组装结果，不调用真实模型。
- **D**：真机上的采集／执行边界复核，当前待实现，不能由替身结果替代。

所有任务、动作、回复和图像均为合成材料。用互不重叠的哨兵区分原任务自身历史、旧查证、旧恢复、Planner 诊断及测试端私有证据；测试替身以不同的合成 PNG 表示不同帧。完整请求快照和比较结果只在测试进程内存中存在，测试结束即释放，不写入生产日志、导出、截图历史或真实服务。不得为验证“不采集人工过程”而采集真实参与者轨迹；可用入口调用计数、禁用的替身接口和合成的迟到回调判定。

## HX-01：VERIFY 新对话不继承旧阶段

**优先级：P0。层级：A、C。状态：未执行。**

**Given：** 原任务对话含合成哨兵 `HX_ORIGINAL_HISTORY`，旧恢复、旧查证和 Planner 内部测试对象分别含不同哨兵；P1 返回合法的普通 VERIFY 目标及所需证据，目标自身不含这些哨兵。

**When：** 协调器开始 VERIFY 并组装其第一个 GUI 请求，随后用本阶段一次合法 wait 的结果组装下一次请求。

**Then：** 两次请求都保留原任务原文和本次检查目标；第一次没有接管前 GUI 历史、Planner 对话或诊断；第二次只新增本 VERIFY 阶段的文本及工具消息。两次均仅附各自唯一当前图，并且工具集合严格为 wait、finish。

**可判定信息：** 内存快照的角色／消息顺序、允许文本、禁用哨兵集合、图片数量及工具名集合；有效阶段为 VERIFY。

**反例：** 将 Planner 所见的原始动作历史拼成“查证背景”发给 GUI，或将上一阶段执行反馈放进工具返回，均失败；即使字段改名或改放 system 消息也失败。

## HX-02：CONFIRM 不借旧证据完成确认

**优先级：P0。层级：A、C。状态：未执行。**

**Given：** P1 返回 COMPLETE＋VERIFY；原任务历史、旧查证及 Planner 报告包含合成旧证据，当前图另有独立标识。

**When：** 进入 CONFIRM，组装其首个 GUI 请求。

**Then：** 请求使用确认阶段模板，包含原任务、此次确认目标及可见最终态说明；不包含旧阶段文本、旧图片、Planner 原对话、执行器诊断或独立评分。只能使用当前图与 wait／finish。原任务中固定的必需值不得被 Planner 目标替换。

**可判定信息：** 模板及阶段选择、原任务原文相等、旧证据哨兵缺席、唯一当前图、只读工具集合。

**反例：** 为提高确认率附上接管前图片、历史“已保存”报告或用户评价，均失败。要求程序逐项更新完成条件后才接受 finish，也失败。

## HX-03：RECOVERY 只接收交付目标与本阶段历史

**优先级：P0。层级：A、C。状态：未执行。**

**Given：** P1 或 P2 交付合法 EXECUTE；Planner 可见的旧历史与本轮检查反馈含专用哨兵，但合成的交付目标及条件只描述全部剩余工作。

**When：** 首次组装 RECOVERY 请求，并在其一次执行后组装下一次请求。

**Then：** 首次只含对应系统／任务提示、原任务原文、完整剩余目标、可观察条件、允许的能力元数据、适用的中性通知及当前图；不继承原任务旧对话、VERIFY／CONFIRM 对话或 Planner 诊断。下一次仅累积 RECOVERY 自身文本和工具消息，旧图不重发。

**可判定信息：** 新阶段上下文中的消息来源、禁用哨兵、交付目标覆盖范围由合成预期值比对、单张当前图及既有剩余额度。

**反例：** 将“上一步结果”“Planner 推理摘要”或旧检查反馈改写后塞进恢复目标之外的隐藏提示，失败。拆分多个条件以新任务或新预算分别执行，也失败。

## HX-04：FALLBACK 恢复原任务文本，但不恢复手机状态

**优先级：P0。层级：A、C；D 为待实现复核。状态：未执行。**

**Given：** 保存的原任务文本／工具对话含 `HX_ORIGINAL_HISTORY`；恢复准备中的文本含不同哨兵；手机状态由可控替身设为归还后的状态，存在用户已改变的合成值。Planner 选择 FALLBACK。

**When：** 组装回退后的下一次 GUI 请求并允许其正常提出动作。

**Then：** 恢复原任务自身文本和工具关联，附共同的中性归还通知与此刻新观察；不注入剩余目标、Planner 回退正文、检查旧反馈或旧图片。回退切换本身不得向执行器发出撤销、重放、重置 App 或恢复快照的动作；之后的模型动作仍按当前状态和原任务正常决策。预算保持既有值。

**可判定信息：** 请求中的原任务历史身份与内容、替身执行器在切换期间的调用数为零、新图身份及预算前后值；D 仅用授权测试数据复核不重置手机状态。

**反例：** 为“恢复原任务”先撤销用户编辑，或把 RECOVERY 对话冒充原任务历史继续，均失败。

## HX-05：Harness 关闭时直接延续原任务

**优先级：P0。层级：A、C。状态：未执行。**

**Given：** Harness 从任务开始即关闭；已经有原任务自身文本历史、已用 GUI 额度和一次正常接管／归还事件。

**When：** 归还检查通过并取得新画面，协调器继续任务。

**Then：** Planner 请求计数保持零；不创建 VERIFY、CONFIRM 或 RECOVERY 对话，不调用恢复规划或注入剩余目标。继续同一原任务文本／工具对话，附与 Harness 开启时相同的中性归还通知和一张新当前图。旧图清理仍按 1.1.0 执行，不被算作 Harness 专属历史切换；GUI 额度不重置。

**可判定信息：** Planner 替身调用数、阶段及上下文身份、通知内容相等、原历史保留、唯一当前图和剩余预算。

**反例：** 关闭 Harness 时省略接管通知，或偷偷运行一次 Planner 只是不显示结果，均失败。

## HX-06：有无 Harness 的信息条件成对一致

**优先级：P0。层级：A、C。状态：未执行。**

**Given：** 从同一合成检查点分出 on／off 两次运行：原任务、接管前自身原任务文本／工具历史、已用／总 GUI 额度、GUI 服务配置与请求参数、动作能力、归还后的合成新图及控制事件相同，只改变 Harness 开关。

**When：** 对两次运行提交同一次合成归还事件，检查归还通知和各自后续请求。

**Then：** 原任务逐字一致、归还通知使用同一版本且内容一致、归还新图相同、预算及 GUI 参数不因开关改变。off 保留原历史直接继续；on 可按已确认方法向 Planner 提供必要证据，并新建检查或恢复对话。两侧均不接收人工过程或隐藏评分。

**可判定信息：** 检查点与通知／当前帧的内存比较，以及固定 GUI 配置、参数、能力和预算的逐字段比较。若加入额外无关差异，应能使验收失败。

**反例：** 要求 on／off 后续 HTTP 请求完全相同、要求恢复阶段也继承同一历史，或强行要求真实人工两次操作轨迹一致，均不是本验收条件。给 off 少一张当前图或更少 GUI 额度，则确实失败。

## HX-07：GUI 永远只附当前图，文本不被顺带截断

**优先级：P0。层级：A、C；D 为待实现复核。状态：未执行。**

**Given：** 同一 GUI 阶段先后使用合成帧 F1、F2、F3，文本历史足以唯一识别每次已接受的模型调用和反馈；旧版兼容输入中还含可识别的 image_url／Base64 及配套“最新附图”包装。

**When：** 分别组装第二次、第三次请求，并覆盖 ORIGINAL、VERIFY、CONFIRM、RECOVERY、FALLBACK 及 Harness off 的适用路径。

**Then：** 每次完整 GUI 请求恰好附一张本次有效当前全屏 PNG；旧图、旧编号／尺寸及误指“所附当前 PNG”的旧包装不重发。需要保留的原任务及阶段文本仍完整，不能借清图自动摘要、截断动作历史或恢复旧图片。无有效当前图时不得发送缺图请求。

**可判定信息：** 图像 content part 数、内存中合成图片标识、包装来源、保留文本序列；D 仅用合成测试页面确认每次观察确为新获取的当前状态。

**反例：** 只是不往相册保存，但旧 messages 仍带 Base64；或为清图连同原任务／工具反馈一起删除，均失败。

## HX-08：清理图片不破坏原生工具消息关联

**优先级：P0。层级：A。状态：未执行。**

**Given：** 合成文本会话含两组已完成、不同 tool_call_id 的 assistant.tool_calls 与 role=tool 消息；其中一条用户消息混合原任务文本、图片及附图包装。

**When：** 清理旧图片、组装下一次请求，并分别通过原任务继续、回退恢复和 Harness off 路径使用该文本会话。

**Then：** 两组工具调用的 id、函数名、合法合成参数及对应工具返回文本保持原样；配对与顺序完整，不产生孤立工具返回、删除调用后遗留返回、重编号或跨阶段拼接。混合消息中的原任务逐字保留，图片及只属于图片的包装去除，再附唯一当前观察。

**可判定信息：** 请求快照中的工具关联图和保留文本逐字段相等；每个被保留的工具返回都能找到同一上下文内对应的调用。

**反例：** 重新生成 tool_call_id 却不改配对返回，或把原阶段工具返回复制进新 VERIFY／RECOVERY 对话，均失败。

## HX-09：Planner 仅附必要边界图且明确最新状态

**优先级：P0。层级：A、C。状态：未执行。**

**Given：** 替身提供接管前已有帧、归还新帧、检查过程中的多张刷新帧及最新检查帧；用明确的合成用途设置需要比较的边界集合。另做接管前帧缺失、同帧多引用及中途错误释放边界帧的变体。

**When：** 分别组装 P1 与 P2 请求。

**Then：** P1 仅有当前归还帧及确有必要的可选接管前帧；P2 仅有最新当前帧及仍需比较的边界帧，不累积 P1 的图片 messages 或检查刷新序列。描述与实际附图一一对应、按帧去重，current_frame_id 唯一指向最新图。缺失的接管前帧为 null，删除其描述和附图；不得为补齐槽位在人工期间拍图。逻辑保留的不同证据帧不超过三种允许槽位。

**可判定信息：** 内存 fake 请求的图片集合与预设用途集合、编号／描述映射、唯一最新标识及采集替身调用序列；只检查逻辑证据帧，不把短暂编码副本误当第四种证据帧。

**反例：** 总是附满三张、把第一次 Planner 的图像消息整体接到第二次，或将旧边界帧标为最新，均失败。

## HX-10：迟到数据、人工过程与隐藏证据不进入有效上下文

**优先级：P0。层级：A、C；D 为待实现复核。状态：未执行。**

**Given：** 请求发出后发生接管并使旧控制权代次失效。替身分别延迟返回旧模型回复和旧截图；测试端另持有从未提供给应用的 `HX_PRIVATE_EVALUATOR`、`HX_HUMAN_TRAJECTORY` 合成哨兵，仅作隔离判定。

**When：** 在暂停中、人工控制及归还后不同时间释放这些旧回调，再组装当前允许的 GUI／Planner 请求。

**Then：** 旧模型回复不触发动作，也不追加为有效 assistant／tool 历史；迟到截图不成为当前图或接管前边界帧。接管请求到归还授权前没有新的有效观察采集；人工输入、触摸、节点变化和私有评分不进入任何模型请求。归还使用新取得的画面，不依赖旧 HTTP 取消确认。

**可判定信息：** 替身采集／派发调用计数、有效历史内容及代次、禁用哨兵缺席、归还帧来源。D 用授权测试页面及入口调用计数复核；不记录真实手势序列或人工画面作为“证据”。

**反例：** 迟到回复虽未执行，却被写入自身成功动作或下轮模型历史；或把人工无障碍事件摘要交给 Planner，均失败。

## HX-11：Planner 自身动作历史只含已完成动作

**优先级：P0。层级：A、C。状态：未执行。**

**Given：** 合成执行结果包括本 Agent 的 completed、rejected、cancelled、unknown、device_error；另有尚未执行的模型提议、finish(completed) 声明及外部合成人工事件。

**When：** 构造 P1／P2 的 own_action_history。

**Then：** 只选择 Agent 自身真正完成执行的动作，不加入失败、未知、取消、仅提议或人工动作。阶段 finish 声明不得冒充已修改业务数据的动作。completed 的输入派发／手势完成记录仍只是自身行为证据，不被转换成“已保存”“任务成功”等未经画面支持的事实；现有动作记录不被改造成隐藏评分。

**可判定信息：** 预置结果表与 own_action_history 的集合比较、动作来源和执行状态，以及不存在额外业务结果推断。该检查使用内存运行时动作文本，不要求生产无内容日志保存参数或目标。

**反例：** 将全部模型输出当作成功动作，或把“输入已派发”升级为“修改已持久化”，均失败。

## HX-12：P2 直接结束不新建 GUI 上下文或附加完成门槛

**优先级：P0。层级：A、C。状态：未执行。**

**Given：** 普通 VERIFY 已合法返回 finish，或 CONFIRM 已合法返回 finish(unable)；P2 得到新的合成当前证据并返回合法 COMPLETE＋FINISH，objective 为空字符串、completion_conditions 为空数组。覆盖 verification_failed=true。GUI 额度刚用完的变体，明确以合法 VERIFY finish 或 CONFIRM finish(unable) 消耗最后一步为前置，不能把没有阶段结束声明的 wait／错误耗尽混入本路径。

**When：** 协调器接受 P2 输出。

**Then：** 直接结束自动流程；不构造新 GUI 请求、done／finish 工具调用、确认目标、逐条件状态或第三次 Planner 请求。不得仅因 verification_failed=true 将合法 COMPLETE 强制改为旧规则的执行／回退，也不得因为 GUI 额度为零而补发或要求额外 GUI 结束声明。结束来源为 Planner 判断，不生成用户已评价或研究者核验成功的事实；不把判断／评分再送回模型。

**可判定信息：** P2 之后请求组装器、模型替身与执行器调用增量为零；原 GUI 已用步数不变，Planner 次数为二，阶段结束来源与用户评价互不替代。

**反例：** 为保持工具对话“完整”再问 GUI 一次 done，或先要求所有 completion_conditions 逐项更新后才结束，均失败。此场景检验路由和信息边界，不声称 Schema 能证明任意截图确实代表任务成功。

**相邻边界：** 若最后一个 GUI 步骤是 wait 或错误、没有合法 finish，且 GUI 额度已为零，按用户最新确认直接以 budget_exhausted 结束，不再调用 P2；不能用本场景的“零 GUI 额度下接受已有 P2 完成判断”反向许可该额外调用。

## 不在本文发明的规则

“仍必要的边界帧”尚无面向任意自然任务的自动语义判定器。HX-09 使用明确用途的合成变体，只验证上限、缺失处理、去重、独立组装和禁止历史归档；不能据此宣称已实现通用最优选图。未完成 GUI 工具调用的本地消息配对处理及真实端点的完整多轮兼容性，需在适配器实现时明确并单独验证，不能伪造工具成功或增加隐藏请求。Planner API／JSON／Schema 错误的原任务回退路径已由基线明确，不是待决事项：P1 失败不另调 P2 修格式，P2 失败也无第三次修复调用。首期不扩展第二轮接管归还或完整 User Study 评分方案。

以上测试用快照和哨兵只用于合成验收，不成为新的生产日志字段、截图留存机制或人工过程采集入口。
