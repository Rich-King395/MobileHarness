## 3. 测试层级

| 层级 | 执行方式 | 能证明的内容与限制 |
| --- | --- | --- |
| C：协调器 | 使用可控时钟、可控模型结果及执行器替身；精确安排回调先后 | 检验控制权代次、单次消费、计账、状态和阶段上限；不证明 Android 实际输入已经停止 |
| A：请求组装 | 内存中查看合成 messages、工具集合、参数、帧引用和调用关系 | 检验模型实际可见信息、图片剥离及原生工具消息配对；不是只检查模板文字 |
| D：设备集成 | 在已授权 Pixel 4 上，以无真实个人数据的测试页面及可控结果源执行 | 验证手势终态、入口、采集生命周期、界面状态与真实派发；不能仅凭预览页面通过 |

可控结果源是验收用替身，不是固定研究任务集或产品必需的电脑控制入口。ADB 可以用于开发安装与测试驱动；最终独立运行的 APK 仍须在断开电脑后完成正常任务链。测试框架和替身的具体实现留到创建工程后决定，不因为写了场景而引入 Appium 等运行依赖。

场景若标 C＋A＋D，所有对应层级通过才算完整验收。真实模型可用于后续连通性／效果检查；迟到、非法输出及边界分支必须由可控结果重现，不能等待商用模型偶然产生某种回答。

## 4. 记号和统一夹具

| 记号 | 含义 |
| --- | --- |
| B／G | 本任务 GUI 总额度／已经发起的实际 GUI 尝试数，默认 B=30 |
| P／V | 本次归还已发起的 Planner 尝试数／已进入的只读阶段数，分别最多 2／1 |
| epoch | 本地控制权归属代次的测试记号；不要求最终实现用此字段名 |
| dispatch | 执行器真正提交手机输入，不是模型提出动作，也不是解析出坐标 |
| F_pre／F_return／F_check | 已存在接管前边界帧／归还后新帧／只读后当前帧；不是人工期间帧 |
| H_original | 原任务文本及原生工具调用／反馈历史，已剥离历史图片及其附图包装 |
| P1／P2 | 第一次／第二次 Planner **实际尝试**；格式错误和传输失败同样占次数 |

默认夹具使用一段包含明确必需值和保存要求的合成任务、可控成功／失败动作及不同的哨兵文本：`OLD_ORIGINAL`、`CHECK_ONLY`、`RECOVERY_ONLY`、`PLANNER_PRIVATE`。哨兵只标记测试消息来源，不代表真实用户信息，也不进入产品配置。

人工期间不生成或采集一套真实轨迹来做验收。C／A 可以注入不属于模型公开证据的合成对象，断言它们始终不可达；D 只由测试人员在授权测试页面进行必要手动更改，归还后看新画面，不录制中间过程。模型的独立效果评价留待 User Study；本套主要检验流程是否遵守设计。

## 5. 统一通过条件

- 事件按本地串行协调规则结算。对“回复有效性检查／解析／排队／真正派发”分别安排交错，不能只测网络响应最后才到的一种顺序。
- 接管后不新增自动派发；接管前已经提交的输入，只有确认终态后才允许显示人工控制。HTTP 取消确认与手机输入终态分别观察。
- 原任务原文、必需值和当前手机状态不被回退改写；所有模型请求只包含所属阶段允许的信息。
- GUI 的 wait、finish、失败和无效决策全部按实际请求计步；人工和控制按钮不扣步；迟到不退款。Planner 另计，无隐藏重试。
- 最多两次 Planner 和一个 VERIFY／CONFIRM 阶段；同阶段多步观察不算多轮。交付执行／回退后不持续重规划。
- P2 合法 COMPLETE＋FINISH 后没有新增 GUI 请求、结束动作或查证。模型完成评估不自动变成用户／研究者成功结论。
- Harness 开关对照使用同样的原任务、接管前有效上下文、控制权过程、新观察、归还通知、预算规则及 GUI 采样／图像／工具协议。合法方法差异是 Planner、阶段隔离及剩余目标；不能要求两条路径的最终 messages 或最终步数完全相同。

## 6. 验收观测与隐私

生产最小日志不能证明所有信息隔离断言。例如“不含旧历史”不能仅从日志里的 phase 标签推断。C／A 的验收替身应在内存中读取已组装请求、执行器派发和帧引用，再输出**无内容的通过／失败结论**。

- 可以持久化：场景 ID、变体、验收契约版本、提示词包 manifest 哈希、实现构建版本、测试层级、PASS／FAIL／BLOCKED／NOT_RUN、无内容断言编号和数字计数。
- 不持久化：真实任务／截图／Base64／Key／完整 messages／模型回复／控件文字／点击坐标／人工轨迹／内存转储。不得为了证明不留截图而导出真实截图或把网络正文写到文件。
- 测试代码中的合成夹具可版本化；真实设备观测仅按最小数据边界短暂处理。若需要核对帧等价，内存比较后只保留布尔断言，不能在普通日志新增截图哈希。
- 测试结束释放请求快照与图像引用。故障报告不得直接保存原始 exception、厂商响应正文或附带用户内容的自动截图。

## 7. 执行与报告要求

先运行 C／A，再在设备验证 D；发现任何计账、隔离或屏障失败时保留失败状态，不能靠换请求 ID、清零计数或重启任务将原失败改记通过。修复后使用新的验收执行记录重跑受影响场景。

每条结果至少写明：场景／变体、层级、构建版本、验收合同版本、提示词包哈希、预期与实际的无内容断言结果。缺少设备或实现时写 NOT_RUN／BLOCKED 及原因，不用“文档检查通过”替代行为通过。失败原因只用约定断言编号和分类，敏感内容留在内存中即时核对。

建议首轮顺序：迟到回复与暂停屏障 → 历史／图片隔离 → 预算精确计账 → 规划及只读上限 → P2 直接结束及零余额边界 → Harness 开关成对检查 → 真实入口与进程中断回归。
